# 室內感測與回饋資料格式 v1

居家環境與外出建議代理人｜第二組｜主責 高群軒

本版供 ESP32、資料接收、分析與 Web 串接。使用單一房間作為第一版驗收情境，保留房間與裝置識別。以下 JSON 均為示範資料。

## 資料由誰產生與使用

| 資料 | 產生者 | 儲存與使用 |
| --- | --- | --- |
| 室內量測 | ESP32 | 高群軒接收、驗證及保存。鍾易憲讀歷史資料做分析，蕭程勻讀最新狀態。 |
| 主動操作日誌 | 操作人員手動記錄 | 高群軒保存。鍾易憲用來核對事件，蕭程勻可查最近已確認的操作。 |
| 候選事件 | 鍾易憲的分析程式 | 高群軒依事件 ID 保存。蕭程勻根據事件發出詢問。 |
| 詢問與回覆 | 蕭程勻的 Web 流程 | 高群軒依事件 ID 保存並提供查詢。鍾易憲讀取已確認及未知的紀錄做評估。 |

## 共通規格

- JSON 欄位採 snake_case。ID 為字串，寫入後維持一致。單房間也保留 room_id。
- 時間欄位使用帶時區的 ISO 8601。後端統一轉為 UTC，格式固定為 `YYYY-MM-DDTHH:mm:ss.SSSZ`。介面可顯示臺灣時間。
- 溫度和相對濕度使用有限的 JSON number。相對濕度的有效範圍是 0–100，缺值以 `null` 表示，0 仍是數值。溫度的合理範圍依選定感測器及使用環境設定。
- 欄位標「可為 null」時，範例保留欄位。寫入介面可由呼叫端省略此類欄位，接收端轉成 `null`。
- MQTT v1 的 topic 暫定為 `aiot/v1/rooms/{room_id}/devices/{device_id}/measurements`，完整名稱由裝置設定帶入。接收端核對 topic 與 payload 的房間、裝置是否一致。
- 取樣頻率、資料過期時間與時間缺口門檻由組員確認後記在設定，以下格式共用於各個門檻。

## 1 室內量測 measurements

### MQTT 上傳欄位

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| schema_version | integer | 固定為 1。 |
| measurement_id | string | 由裝置產生的唯一量測 ID。建議用裝置 ID、每次啟動的唯一識別、取樣序號組合。重送同一筆時沿用原 ID。 |
| room_id | string | 房間識別，由配置提供。 |
| device_id | string | 感測裝置識別，由配置提供。 |
| measured_at | string | 實際採樣時間。裝置取得有效時間後再上傳。 |
| temperature_c | number 或 null | 攝氏溫度，感測器讀取失敗填 null。 |
| relative_humidity_pct | number 或 null | 相對濕度百分比，感測器讀取失敗填 null。 |

```json
{
  "schema_version": 1,
  "measurement_id": "sensor-01:boot-a27:123",
  "room_id": "room-01",
  "device_id": "sensor-01",
  "measured_at": "2026-11-18T10:00:00.000Z",
  "temperature_c": 27.4,
  "relative_humidity_pct": 68.2
}
```

### 接收、保存及查詢

接收端在量測紀錄加上兩個欄位，ESP32 上傳只需上表的欄位。

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| received_at | string | 接收端第一次收到此量測的時間。 |
| quality_flag | string | `ok` 兩值通過檢查、`missing` 有空值、`invalid_range` 量測超出合理範圍。若同筆兼有越界和缺值，採 `invalid_range`。 |

- `measurement_id` 為唯一鍵。相同 ID 與相同原始欄位重送時，只保留一筆。相同 ID 卻帶不同內容時，記錄衝突並保留原資料。
- 若 payload 缺識別欄位、欄位型別錯誤或時間無法解析，記錄接收錯誤。可解析且感測值缺少時，保留該筆並標記品質。
- 最新量測依 `measured_at` 選取，回傳原讀值、量測時間及品質。過期時由查詢端另回傳 `is_stale: true`，新鮮時為 `false`。查無資料回傳空結果。資料品質與時效是兩項獨立判斷。
- 歷史查詢至少能用 `room_id` 與 `[from, to)` 過濾，依量測時間排序。分析工具先依品質挑選有效讀值，再按時間缺口切開視窗。斷線重連後，保留缺口供分析判斷。

## 2 主動操作日誌 operation_logs

回饋詢問之外，記錄成員實際操作或在指定時段內觀察到的無操作情境。主動操作日誌可以早於候選事件建立。

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| operation_id | string | 操作日誌唯一 ID，由接收端核發。 |
| room_id | string | 所屬房間。 |
| operation_at | string | 實際操作時間。有多筆動作時拆開紀錄。若為無操作，記錄觀察時段起點。 |
| observation_end_at | string 或 null | 無操作觀察的結束時間，且須晚於起點。設備操作時為 null。 |
| operation_label | string | `ac`、`dehumidifier`、`window` 或 `none`。 |
| action | string 或 null | 家電為 `on`／`off`，窗戶為 `open`／`close`，`none` 為 null。 |
| recorded_at | string | 高群軒的資料接收端保存這筆日誌的時間。 |

```json
{
  "operation_id": "op-001",
  "room_id": "room-01",
  "operation_at": "2026-11-18T10:01:00.000Z",
  "observation_end_at": null,
  "operation_label": "ac",
  "action": "on",
  "recorded_at": "2026-11-18T10:01:30.000Z"
}
```

冷氣與除濕機同時操作時，日誌各記一筆，分析可把同一事件下的兩筆操作標成混合。查設備狀態時以有時間及動作的確認紀錄為依據，依有效時間判斷是否仍適用。只知道「曾操作」或缺乏近期確認時，狀態回為 `unknown`。

## 3 候選事件 events

由鍾易憲產生 `event_id` 和趨勢特徵，高群軒負責持久化。事件延續時由分析端用原 ID 更新。

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| event_id | string | 候選事件唯一 ID，由分析端產生。 |
| room_id | string | 事件對應的房間。 |
| start_at | string | 事件偵測到的起始時間。 |
| end_at | string 或 null | 事件仍持續時為 null。 |
| detected_at | string | 分析端辨識此事件的時間。 |
| features | object | 趨勢特徵，B 提供欄位字典和版本。溫度差用 °C，RH 差用百分點。 |
| quality_flag | string | `ok` 或 `gap`。碰到量測缺口的視窗保留品質資訊，交由分析端排除或重建視窗。 |
| event_version | integer | 初次保存為 1。同一事件更新時遞增，用於辨識重送或過時更新。 |

```json
{
  "event_id": "evt-001",
  "room_id": "room-01",
  "start_at": "2026-11-18T10:02:00.000Z",
  "end_at": null,
  "detected_at": "2026-11-18T10:08:00.000Z",
  "features": {
    "temperature_delta_c": -1.3,
    "relative_humidity_delta_pct_points": -4.2
  },
  "quality_flag": "ok",
  "event_version": 1
}
```

事件應先完成儲存，再由 Web 以該 ID 發出詢問。實際操作以使用者確認及日誌核對。分析匯出時保留判斷當下的特徵，事後更新的特徵需帶對應版本。

## 4 詢問與回覆 feedback

Web 每次發出詢問產生一個 `feedback_id`，同一個 `event_id` 可關聯多次詢問。首次發問寫入 `pending`，送出回覆時沿用原 `feedback_id`。C 提供詢問與回覆資料，A 依下列規則保存。

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| feedback_id | string | 詢問及其回覆的唯一 ID，由 Web 產生。重送同一筆時沿用。 |
| event_id | string | 對應已保存的候選事件。 |
| asked_at | string | 實際發出詢問的時間。 |
| expires_at | string | 此次詢問的回覆期限。 |
| replied_at | string 或 null | 實際送出回覆的時間。等待或逾時未回覆時為 null。 |
| operation_at | string 或 null | 使用者提供的實際操作時間，無法確認、混合操作時間不同或無操作時可為 null。 |
| operation_label | string 或 null | `ac`、`dehumidifier`、`window`、`mixed`、`none` 或 `other`。未知時為 null。 |
| status | string | `pending` 等待、`confirmed` 已確認、`uncertain` 使用者不確定、`expired` 逾時未回覆。 |

儲存與查詢另含 `feedback_version`（從 1 開始的整數）與 `updated_at`（接收端寫入該版本的時間）。Web 更正時帶上查到的版本，接收端核對後寫入下一版並保留舊版。下方為 Web 送出的回覆內容範例。

```json
{
  "feedback_id": "fb-001",
  "event_id": "evt-001",
  "asked_at": "2026-11-18T10:08:20.000Z",
  "expires_at": "2026-11-18T10:23:20.000Z",
  "replied_at": "2026-11-18T10:09:00.000Z",
  "operation_at": "2026-11-18T10:01:00.000Z",
  "operation_label": "ac",
  "status": "confirmed"
}
```

| 狀態 | 回覆時間 | 操作標記 | 評估用途 |
| --- | --- | --- | --- |
| pending | null | null | 等待回覆。 |
| confirmed | 必填 | 必填 | 可納入標記候選。和日誌衝突時先核對。 |
| uncertain | 必填 | null | 保留使用者有回覆但不確定。 |
| expired | null | null | 保留逾時與未回覆。 |

- `none` 只用於明確確認無操作的回覆。分類評估將同一事件的操作日誌和回覆核對後，以事件為單位計數。
- 重送同一筆資料可安全重試。晚到回覆或使用者更正應留存原有效紀錄與更新時間，查詢時回傳最新版本，評估時可追溯當時狀態。晚到可由 `replied_at > expires_at` 判斷。
- 上面範例的時間均為 UTC。10:01 操作冷氣，10:08:00 偵測到變化，10:08:20 發問，10:09:00 回覆。設備開啟動作來自操作日誌，事件回覆提供確認的操作類別。

## 串接驗收 checklist

- [ ] A 以一筆實測驗證 MQTT 收到的欄位、SQLite 保存結果及最新量測查詢一致。
- [ ] A 重送同一量測，查回一筆。另送兩筆皆可解析的缺值及超界資料，各自保留正確的品質狀態。
- [ ] A 與 B 查詢同一時段的歷史紀錄，核對半開時段、資料排序，以及斷線前後的視窗切分。
- [ ] B 建立事件與更新版本，C 以同一 `event_id` 發問，A 保存已確認的回覆，三人能查回相同關聯。
- [ ] C 補測不確定、未回覆及更正，A 能查回對應狀態，B 的評估仍能區分未知與明確無操作。

開工前先與鍾易憲確認事件特徵與查詢視窗，與蕭程勻確認詢問狀態及回覆欄位。取樣頻率、過期門檻和時間缺口門檻待首次實測後記錄。
